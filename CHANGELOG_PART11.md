# Phase 2 / Part 4 — Tasks, Ads & Contests (v1.11.0)
## What's new
- **Tasks with proof** (bot / website). Mark a task "Proof required" in Admin > Tasks (or let an approved bot / website campaign become one). The user opens the task, then sends a short proof (their @username, a code the bot showed, a link; 3-300 characters). **Admin > Task proofs** lists them: Approve pays the task reward once, Reject needs a reason and the user can try again (3 attempts per task, 5 proofs waiting per user; both editable). A timer or a click can never pay a proof task. `ALLOW_UNVERIFIED_TASKS` stays gone / false.
- **Ad delivery**. An approved campaign is a task in Tasks; every completion is verified (channel = Telegram `getChatMember`, bot / website = proof when proofs are ON, otherwise the old timer) and written to `campaign_completions`. `campaigns.spent` counts the budget used. When the last completion lands the campaign becomes **finished**. **Owners can now stop a running campaign** (More > Advertise > "Stop and refund unused"); admins can cancel too. Refund = `reward × target − spent`, paid once (ledger ref `cmprefund:<id>`). Campaign cards show used / unused Points.
- **Referral contests** (More > Contests, Admin > Contests). Weekly (7 days), monthly (30 days) or custom (1-90 days). Prizes per rank (e.g. 5000, 3000, 1000), minimum qualified referrals to win (default 1), one contest at a time. Live leaderboard counts qualified referrals inside the window (blocked inviters never count). **Ties**: more referrals first; same number → whoever reached it first; same instant → lower Telegram ID. Ranks are always unique, no prize is split. After the end date the admin types `PAY`: winners are credited once each (`Contest Prize`, ref `contest:<id>:<user>`), the final standings are stored in `contest_entries`, audit `contest.pay`. If a payout stops half-way the contest stays "paying" and **Pay again** only pays who is still unpaid. Cancel (before payout) pays nothing.
- **Settings** (group "Tasks, Ads & Contests"): `task_proof_enabled` (**OFF**), `task_proof_max_pending` (5), `task_proof_max_tries` (3), `contests_enabled` (**OFF**).
- **DB**: `010_tasks_ads_contests.sql`: `task_proofs`, `campaign_completions`, `contests`, `contest_entries`, `tasks.proof_required / proof_hint`, `campaigns.spent / finished_at`, status `finished`. Existing running campaigns are back-filled (`spent`, completions, auto-finish).
- **API**: `taskProofSubmit`, `contests`, `adminTaskProofs`, `adminTaskProofApprove`, `adminTaskProofReject`, `adminContestList`, `adminContestCreate`, `adminContestCancel`, `adminContestPay`. `campaignCancel` now also stops active campaigns. `bootstrap.tasks` has `proof_required / proof_hint / proof_status / proof_reason`.
- **Tests**: +23 (`tests/tasks.test.js`) → 146 passing: proof state machine, attempt limits, budget maths (spent never above budget, paid + refunded = budget), refund once, contest ranking and ties, SQL shape, migration, wiring, UI.
## How the money rules are enforced
- **Proof approval** is ONE SQL statement: proof status + `task_completions` row + task counter + campaign budget + balance + ledger. It uses the **same** `task_completions` UNIQUE and the **same** ledger reference (`task:<task>:<user>`) as the normal claim, so one user can be paid once per task by any route.
- **Closing a campaign** is ONE statement (compare-and-set status, task switched off, refund, ledger). The task row is locked (`FOR UPDATE`) by every claim, so a claim that commits first is counted in `spent` and not refunded; one that arrives later sees an inactive task and pays nothing.
- **Contest prizes** are created Points, like game prizes: check the total shown when you create the contest.
